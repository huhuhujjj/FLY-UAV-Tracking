## 三、技术栈与运行方法

### 3.1 语言、框架与构建工具

- **后端**：Python 3（标准库 `http.server` + `ThreadingHTTPServer`），无第三方 Web 框架；推理依赖 `ultralytics` + `torch` + `opencv`（由 pipeline 引入）。
- **前端**：原生 HTML + CSS + JavaScript（无框架、无构建步骤）。
- **测试**：后端 `unittest`；浏览器端 `Playwright`（Chromium）。
- **构建工具**：无（无需编译/打包）。

### 3.2 包管理器、依赖清单与锁文件

- **Python 推理环境**：`model/requirements-inference.txt`（顶层约束：`ultralytics==8.4.215`、`trackeval==1.3.0`、`lap==0.5.12`）；完整锁定清单 `model/requirements-inference-windows-lock.txt`（本机实际运行环境）；虚拟环境 `model/.venv`（Python 3.12.14）。
- **Node**：`web/backend/package.json` + `package-lock.json`（仅 `playwright@^1.49.1` 及 playwright-core，用于 E2E，后端运行不依赖 Node）。
- **注意**：项目根目录的 `requirements-lock.txt` 是**另一个更早的 CUDA 13 环境**（torch 2.13.0+cu130、ultralytics 8.4.177），与当前推理环境不一致，**不要**用它来搭建本测试界面。

### 3.3 从零搭建与运行命令（完整、含版本）

**本机实测关键版本**（`model/.venv`，Python 3.12.14）：

| 依赖 | 版本 |
|------|------|
| torch | `2.10.0+cu128`（CUDA 12.8 构建） |
| torchvision | `0.25.0+cu128` |
| ultralytics | `8.4.215` |
| opencv-python | `5.1.0.95` |
| numpy | `2.5.4` |

以下命令为**统一 PowerShell 语法**（Windows 环境），可逐条直接执行；关键点：**不激活虚拟环境**，而是直接用虚拟环境的解释器 `model\.venv\Scripts\python.exe -m pip` 安装与运行，避免激活脚本的歧义和安装位置出错。

```powershell
# 0. 进入项目根目录（pipeline 与后端均以此为基准）
cd C:/Users/LYXIh/Desktop/FPY/UAV_Video_Tracking

# 1. 创建 Python 虚拟环境（Python 3.12.x）
python -m venv model/.venv

# 2. 安装 PyTorch（当前唯一已验证的可复现环境：CUDA 12.8 构建，必须指定 PyTorch 官方 cu128 index）
#    注意：锁定清单 requirements-inference-windows-lock.txt 中的版本带 +cu128 后缀，
#          是 CUDA 12.8 专用构建；CPU 版 torch 的版本号不含 +cu128，二者不可互换。
model/.venv/Scripts/python.exe -m pip install torch==2.10.0+cu128 torchvision==0.25.0+cu128 --index-url https://download.pytorch.org/whl/cu128

# 3. 安装其余推理依赖（含 ultralytics / opencv / numpy / trackeval / lap）
model/.venv/Scripts/python.exe -m pip install -r model/requirements-inference.txt
#    需完全复现锁定版本时，可改用：
#    model/.venv/Scripts/python.exe -m pip install -r model/requirements-inference-windows-lock.txt

# 4.（可选，仅跑 E2E 时）安装 Playwright 与 Chromium
cd web/backend
npm install
npx playwright install chromium
cd ../..

# 5. 确认权重就位（若缺失需先下载 yolo26l.pt 放入 model/weights/）
if (Test-Path model/weights/yolo26l.pt) { Write-Host "权重已就位" } else { Write-Host "缺少 model/weights/yolo26l.pt" }

# 6. 启动本地测试服务（仅本机可访问）
model/.venv/Scripts/python.exe web/backend/run.py
# 启动成功打印：
#   Serving local UAV test interface at http://127.0.0.1:8765/
#   Stop with Ctrl+C. Only this machine can reach this service.
```

- **访问地址**：`http://127.0.0.1:8765/`（自动重定向到 `workspace.html` 工作台索引页）。
- **端口**：`8765`（可用环境变量 `UAV_PORT` 覆盖）。
- **提示**：若本机已存在可用的 `model/.venv`，可直接跳到第 6 步启动，无需重新安装。
- **说明**：`requirements-inference.txt` 中未固定 torch/torchvision 版本（由第 2 步显式安装），故第 3 步安装的其余依赖不会覆盖 torch。
- **CPU 环境（另行验证）**：以上命令为 **CUDA 12.8（+cu128）环境，是本项目唯一已验证的可复现环境**。若改用 CPU 环境，需将第 2 步换成 PyTorch 官方 CPU index（`https://download.pytorch.org/whl/cpu`）并使用 CPU 版 torch（版本号不含 `+cu128`），但**该路径未在本项目验证**，CPU 推理速度与功能一致性需另行确认，不能视为已复现。`requirements-inference-windows-lock.txt` 中的 torch 版本带 `+cu128` 后缀，**不能**用 `--index-url` 的 CPU 源安装出对应版本。

### 3.4 运行目录、端口与环境变量

| 项 | 值 | 说明 |
|----|----|----|
| 运行目录 | `UAV_Video_Tracking`（项目根） | server 用 `__file__` 定位 `model/` 与 `web/frontend`，不受 cwd 影响，但推荐从根启动 |

### 3.5 是否依赖网络/CDN/外部资源

- **完全离线**。无 CDN、无外部字体、无远程图片、无第三方网络请求。所有图标为内联 SVG，字体为系统默认，样式本地引用。
- 仅首次安装 Playwright/推理依赖时需要网络；运行与推理不需要网络。

### 3.6 无需构建、直接打开 HTML 是否可行

- **不可以直接双击 HTML 运行功能**。功能页依赖同源后端 API（`fetch`），必须通过 `run.py` 启动本地服务后访问 `http://127.0.0.1:8765/`。
- 仅任务历史页、评估记录页两个纯静态页可在无后端时直接打开浏览（但会失去服务状态提示）。

### 3.7 已知安装/启动问题

- 首次推理会加载 `yolo26l.pt`（53 MB）与 ultralytics/torch，CPU 模式下启动较慢，属正常现象。
- 若 `model/.venv` 缺失或未装 ultralytics/torch，后端启动可成功但提交任务会返回 `FAILED`（pipeline 导入失败），需先补齐推理环境。
- E2E 测试依赖 Playwright 已安装的 Chromium；未安装需执行 `npx playwright install chromium`。

### 7.2 示例数据文件位置与字段

  - `tracks.json`、`frames.jsonl`、`run.json`（含 `status/frame_count/detection_count/video/config/elapsed_seconds` 等）

### 7.3 前端状态保存/更新/清理

- 前端状态集中在 `app.js` 的 `state` 对象（`mediaType/fileName/file/currentJob/polling/pollTimer/submitting`）。
- 状态随页面操作即时更新；任务结果不落前端存储。

### 7.4 刷新后保留/丢失与恢复边界（重要）

- **浏览器刷新（页面重载）**：
  - **保留**：语言偏好（`localStorage`）；最近一次任务通过 `restoreLastJob()` 从 `/api/jobs` 恢复，非终态任务会自动续轮询。
  - **丢失**：当前未提交的文件选择（刷新后需重新选择）。
  - 前提是**后端服务仍在运行**——`/api/jobs` 返回的是后端进程内存中的记录。
- **后端服务重启（或进程退出）**：
  - **任务记录保存在内存**（`server.py` 的 `_JobStore._jobs`，见 `server.py` 第 60 行起的 `_JobStore` 类），**未持久化到磁盘**。服务重启后，`/api/jobs` 返回空，历史任务无法在界面中恢复。
  - 磁盘上残留的产物目录 `web/backend/jobs/<job_id>/` **不会**被新进程重新索引或展示。
  - 即：**「刷新可恢复（服务在跑）」，但「服务重启后的恢复尚未实现」**，这是明确的边界，不可描述为已支持持久化恢复。

### 7.5 存储机制

- **localStorage**：仅语言偏好（i18n.js）。
- **后端任务元数据**：`server.py` 的 `_JobStore`（进程内存字典），**无持久化**，服务重启即丢失。
- **产物文件**：存于后端 `web/backend/jobs/<job_id>/run/artifacts/`（磁盘），服务重启后仍在磁盘但不再被索引。
- **未使用**：sessionStorage、IndexedDB、浏览器缓存（API 均 `cache: "no-store"`）。

### 7.6 需迁移到服务端的业务逻辑

- 文件类型/大小校验在前端做了镜像，权威校验已由后端承担，无需迁移。
- 检测表分页/截断（500 条上限）逻辑在后端 `_read_detections`，前端仅展示，合理。
- 暂无明显应迁移的纯前端业务逻辑；若后续加筛选/统计，应在后端实现。

### 7.7 需释放的资源

- **轮询定时器**：`pollJob()` 的 `setInterval` 在终态后 `clearInterval`；`resetWorkbench` 亦清理。
- **健康检查定时器**：`init()` 中 `setInterval(checkHealth, 5000)` 为长期运行，页面卸载时未显式清理（影响轻微）。
- **媒体对象**：`<video>`/`<img>` 由 DOM 重建时自然释放，无手动 URL 撤销。
- **后端线程**：`_run_job` 为 daemon 线程，随进程退出。

## 八、前后端接口与集成准备

已有后端，接口清单如下（`server.py`）：

| 方法 | 路径 | 用途 | 调用位置 |
|------|------|------|----------|
| GET | `/api/health` | 服务状态 | app.js `checkHealth`；workspace 内联 |
| GET | `/api/jobs` | 任务列表 | app.js `restoreLastJob`/`checkHealth` |
| POST | `/api/jobs` | 提交任务（multipart） | app.js `apiPostJob` |
| GET | `/api/jobs/<id>` | 任务详情/状态 | app.js `pollJob` |
| GET | `/api/jobs/<id>/detections` | 检测明细 | app.js `renderDetectionTable` |
| DELETE | `/api/jobs/<id>` | 取消非终态任务 | app.js `cancelJob` |
| GET | `/api/artifacts/<id>/<name>` | 产物下载/媒体（支持 Range） | app.js `buildDownloadList`/结果区 |

### 8.1 请求/响应与脱敏示例

接口列表为 `GET /api/jobs`（**无尾斜杠**，`server.py` 第 380 行精确匹配 `path == "/api/jobs"`，`/api/jobs/` 不会被等同处理，会落入 `/api/jobs/<id>` 分支且因 job_id 为空/不匹配返回 404），返回 `{"jobs":[...]}`，数组元素为 `_job_status_payload` 结构。

- **POST /api/jobs**：`multipart/form-data`，字段 `file`。可选 query：`device`、`imgsz`、`conf`、`iou`、`max_det`。
  - 成功返回 `202`：单个任务对象（`_job_status_payload`，含 `job_id/status/media_type/input_name/created_at/error/artifacts/run`），例如 `{"job_id":"<12位hex>","status":"WAITING","media_type":"image","input_name":"...","artifacts":[],"run":null}`
  - 冲突返回 `409`：`{"error":"busy","message":"已有任务在处理中，请等待完成后再提交。"}`
- **GET /api/jobs**：`200`，返回 `{"jobs":[ <任务对象>, ... ]}`；每个任务对象含 `job_id`、`status`、`media_type`、`input_name`、`created_at`、`error`、`artifacts`（名称+字节数）、`run`（`frame_count/detection_count/video/config/elapsed_seconds`）。
- **GET /api/jobs/<id>**：`200`，返回单个任务对象（同上结构）。
- **状态枚举**：`WAITING / RUNNING / SUCCEEDED / FAILED / INTERRUPTED`。

### 8.2 错误码、超时与重试

- HTTP 语义：`400` bad_request、`404` not_found、`409` busy/already_terminal、`413` too_large、`415` unsupported_type、`403` forbidden（路径穿越）、`416` 范围不满足。
- **无显式超时**；前端轮询间隔 1.2s（`pollJob` 的 `setInterval`，`app.js` 第 232 行起）。
- **轮询失败无重试次数上限、也无停止逻辑**：`pollJob` 的 `.catch()` 为**空操作**（注释 `transient; keep polling a few more times`，实际未计数、不退出），因此单次请求失败后定时器会**继续每 1.2 秒轮询**，直到任务进入终态（`isTerminal`）才 `clearInterval`。若服务长时间不可达，轮询会无限持续（仅受页面生命周期约束），不会自动停止。
- 无自动重试上传（用户手动重新提交）。

### 8.3 文件上传、结果获取、进度更新

- **上传**：一次性 `multipart/form-data` 单文件（后端手写 `_parse_multipart_single_file` 解析）。
- **结果获取**：提交后轮询 `/api/jobs/<id>`，终态后拉取检测明细与产物。
- **进度**：无百分比进度，仅有状态机（WAITING → RUNNING → 终态）。

### 8.4 代理、CORS 与服务地址

- **无 CORS 需求**：前端与 API 同源（均由 `127.0.0.1:8765` 提供）。
- **无代理**：本地直连。
- 服务地址常量：前端 `API = {health:"/api/health", jobs:"/api/jobs"}`（相对路径）。

| 输入/临时/结果文件保存与清理 | **已实现** | 上传副本处理后 `source.unlink` 删除；产物保留在 `jobs/<id>/` |

### 9.1.1 取消任务的实际含义（重要，须明确）

当前「取消」**不是**对推理计算的即时中断，而是「结果不发布」。具体机制：

- 前端 `cancelJob()` 发起 `DELETE /api/jobs/<id>`；后端 `do_DELETE` 仅调用 `STORE.mark_cancel_requested(job_id)` 设置一个**内存取消标记**（`server.py` 第 481 行），并不终止正在执行的 worker 线程。
- 后端 `_run_job`（`server.py` 第 201 行起）在**调用 `run()` 返回之后**才检查该标记（第 215 行 `if STORE.cancel_requested(job_id)`），若已取消则把状态置为 `INTERRUPTED` 且**不发布产物**（`artifacts=[]`、`run_summary=None`）。
- `model/src/pipeline.py` 的 `run()` 内部是**逐帧循环一次性跑完，无任何取消检查点**；因此：
  - **运行中点击取消，CPU/GPU 上的推理计算会继续执行到自然结束**，不会中途省下算力；
  - 取消的唯一效果是：任务最终标为 `INTERRUPTED`、前端不展示/不发布结果；
  - 对长视频而言，取消后用户仍需等待该次推理跑完，才能释放单任务槽并提交新任务。

这属于当前实现的已知限制，不应描述为「取消能立即停止计算」。若后续需要真正的即时中断，需在 `run()` 的逐帧循环中加入取消检查点（或改为可中断的子进程/协程），并扩展 server 与 pipeline 之间的取消信号通道。

### 9.1.2 单任务锁与取消的相互影响

- 单任务锁在 `_start_job` 通过 `STORE.active_nonterminal_exists()` 实现；取消后任务在 worker 真正结束前仍被视为「非终态」（`_worker_done` 为 False），因此**取消后需等 worker 释放 pipeline 文件锁才能提交新任务**。
- 这与 9.1.1 一致：取消不省算力，反而会占用锁直到本次推理自然结束。
